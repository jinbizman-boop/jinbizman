* WBS를 전 직군 공통 양식으로만 운영하면 기획/디자인/개발/운영/재무의 실제 업무 방식이 반영되지 않아 기록은 남아도 관리 품질이 떨어집니다.
* 인사평가를 단순 보고 횟수나 상사 주관 판단으로 처리하면 공정성이 무너집니다.
* 업무보고·업무일지와 프로젝트/WBS가 분리되면 진척도 수치화가 불가능해집니다.
* 다국어를 문자열 덧붙이기 방식으로 붙이면 페이지별 품질이 무너지고, 언어별 발행 관리가 불가능해집니다.
* 반응형을 외부 페이지만 적용하고 ERP는 데스크톱 전용처럼 만들면 실제 운영에서 모바일/태블릿 현장 대응이 무너집니다.

# JINBIZ ERP 시스템 기반 관리자 페이지 기획안

## 최신형 완성형 최종본

기준 문서상 진비즈 관리자 시스템은 이미 **단순 CMS가 아니라 ERP**로 정의되어 있고, 범위 역시 **홈페이지 운영 / 뉴스·공지 / 문의·리드 / 전자결재 / WBS·프로젝트 / 조직·인사·근태 / 경비·정산·재무 / 문서·지식관리 / 리포트·통계 / 시스템 관리**를 포함하는 통합 운영 구조로 잡혀 있습니다. 또한 외부 홈페이지는 회사소개형 AI 서비스 기업 사이트로, 내부는 WBS 중심 ERP로 고정되어 있습니다.  

따라서 이번 최종안의 정의는 아래처럼 확정하는 것이 맞습니다.

> **JINBIZ ERP는 홈페이지 관리 백오피스가 아니라,
> 서비스 운영·프로젝트 실행·업무 보고·업무 일지·결재·문의 전환·조직 운영·평가까지 연결하는 통합 운영 OS다.**

그리고 이번 기획안의 핵심은 아래 5개입니다.

> **첫째, 모든 업무는 WBS를 중심으로 관리된다.**
> **둘째, 아침 업무보고와 퇴근 전 업무일지로 프로젝트 진척도와 완성도를 실시간 추적한다.**
> **셋째, 홈페이지 운영은 단일 사이트 관리가 아니라 새 앱/홈페이지를 연결만 하면 바로 관리 가능한 확장형 구조로 설계한다.**
> **넷째, ERP와 외부 운영은 `www.jinbizman.com` 기준의 통합 도메인 정책 위에서 운영한다.**
> **다섯째, 외부와 내부 운영은 반응형·다국어를 포함한 글로벌 운영 구조를 처음부터 가진다.**

## 1. 이번 최종안에서 확정하는 기본 전제

기존 기준 문서에서 확정된 사항은 그대로 유지합니다.

* 관리자 페이지는 **처음부터 ERP 시스템**으로 간다.
* 외부 홈페이지 운영도 ERP 내부 모듈로 관리한다.
* 뉴스레터 메뉴는 실제로 **보도자료 / 공시정보 / 공지사항** 구조로 운영한다.
* 문의는 **이메일 알림 + 관리자 저장**을 동시에 처리한다.
* 플랫폼 사례는 관리자에서 계속 등록·수정·아카이브할 수 있어야 한다.
* ERP는 단일 계정 체계, 모듈형 연결 구조, 결재 중심 운영, 프로젝트/WBS 중심 운영을 기본 원칙으로 가져간다.

이 기본 전제 위에 이번에 정식으로 추가되는 고도화 포인트는 다음입니다.

* **멀티 서비스 연결형 홈페이지/앱 운영 구조**
* **직무·직군·업무유형별 맞춤 WBS 체계**
* **공정성과 재현성을 갖춘 인사평가 체계**
* **PC·모바일·태블릿 전 기기 반응형 ERP/운영 웹앱**
* **한국어·영어·일본어·불어·스페인어 공식 지원**
* **대표 도메인 `www.jinbizman.com` 통합 운영**

이 방향은 외부 홈페이지의 정보 구조, 내부 ERP 방향, 서비스 허브, WBS/업무보고, 평가 근거 데이터까지 포함해 첨부 문서들이 반복해서 가리키는 기준과 일치합니다.

## 3. 전체 구조의 핵심 원칙

### 원칙 1. 모든 일은 프로젝트에 속한다

업무는 반드시 프로젝트 또는 운영 프로그램에 속해야 합니다.

### 원칙 2. 모든 실무는 WBS에 속한다

자유 텍스트 업무가 아니라 구조화된 WBS 업무 단위로 관리해야 합니다.

### 원칙 3. 모든 보고는 WBS와 연결된다

아침 업무보고와 퇴근 전 업무일지는 WBS 없는 상태로 작성할 수 없어야 합니다.

### 원칙 4. 모든 홈페이지/앱 운영은 서비스 단위로 연결된다

새 서비스가 생길 때마다 관리자 페이지를 다시 만드는 방식이 아니라, **서비스 레지스트리**에 등록하면 기존 관리자에 붙는 구조여야 합니다.

### 원칙 5. 인사평가는 기록이 아니라 근거로 한다

보고를 많이 썼다고 좋은 평가를 받는 것이 아니라, **어떤 WBS를 맡았고, 어떤 산출물을 냈고, 어떤 품질과 일정 준수율을 보였는지**를 근거로 평가해야 합니다.

### 원칙 6. 모든 공개 운영은 `www.jinbizman.com`을 기준으로 한다

외부 공개 페이지, 공개 뉴스, 문의 완료, SEO canonical, 언어별 링크는 모두 `www.jinbizman.com` 기준으로 정리해야 합니다.

### 원칙 7. 모든 주요 화면은 반응형 웹앱으로 구현한다

외부 홈페이지와 내부 ERP 모두 PC·모바일·태블릿에서 깨짐 없이 동작해야 합니다.

### 원칙 8. 공식 운영 언어는 5개다

한국어, 영어, 일본어, 불어, 스페인어를 공식 지원하고, ERP는 이 5개 언어의 콘텐츠 관리와 발행을 지원해야 합니다.

# 4. 홈페이지 관리 고도화

## “단일 사이트 관리자”가 아니라 “멀티 서비스 운영 허브”로 설계

사용자가 가장 중요하게 추가한 조건 중 하나는 이것입니다.

> **새로운 앱이나 홈페이지가 개발되어 출시되었을 때, 연결만 하면 바로 관리자 페이지에서 관리될 수 있어야 한다.**

이 요구를 만족하려면 홈페이지 운영 모듈을 “페이지 편집기” 수준으로 설계하면 안 됩니다. 처음부터 **서비스 허브형 운영 구조**로 설계해야 합니다. 실행 문서와 백엔드 가이드도 확장성 핵심을 서비스 허브로 보고, 새 서비스가 생겨도 서비스 등록만으로 연결돼야 한다고 정리합니다.  

---

## 4-1. 최종 정의

> **홈페이지 운영 모듈은 특정 사이트 전용 CMS가 아니라,
> 여러 홈페이지·랜딩페이지·웹앱·모바일앱 운영 설정을 하나의 관리자에서 관리하는 멀티 서비스 운영 허브로 설계한다.**

---

## 4-2. 관리 단위

ERP 안에서 관리 대상은 아래처럼 “서비스” 단위로 등록합니다.

### 서비스 유형

* 회사 공식 홈페이지
* 제품/서비스 소개 홈페이지
* 플랫폼 랜딩페이지
* 이벤트/캠페인 마이크로사이트
* 웹앱
* 모바일앱 운영 설정
* 고객지원/헬프센터
* 관리자 서브포털

즉, `www.jinbizman.com`만 관리하는 것이 아니라 향후 **유레카월드**, 신규 플랫폼, 별도 서비스 사이트, 앱 운영 항목까지 모두 같은 구조로 붙일 수 있어야 합니다.

---

## 4-3. 서비스 레지스트리 구조

관리자 안에 **서비스 허브**라는 최상위 운영 개념을 둡니다.

각 서비스는 아래 값을 가집니다.

* 서비스명
* 서비스 코드
* 서비스 유형
* 브랜드명
* 운영 상태

  * 준비중
  * 운영중
  * 점검중
  * 종료
* 연결 도메인
* 연결 환경

  * local
  * staging
  * production
* 관리자 노출 여부
* 담당 부서
* 운영 담당자
* 기술 담당자
* 기본 권한 템플릿
* 콘텐츠 모델
* 배포 방식

* **다국어 여부**

## 5-1. 반응형 웹앱 최종 정의

# 6. WBS 중심 운영 체계

## ERP의 가장 중요한 핵심축

기준 문서에서도 WBS/프로젝트는 진비즈 ERP의 차별화 핵심으로 잡혀 있습니다. 이번 최종안에서는 이를 더 강하게 **운영의 중심 엔진**으로 확정합니다. 업무보고·업무일지·산출물·평가 근거는 모두 WBS와 연결되는 구조가 핵심입니다. 

---

## 6-1. 일일 운영 표준 흐름

### 1단계. 프로젝트 생성

모든 일은 프로젝트 또는 운영 프로그램으로 시작합니다.

### 2단계. WBS 생성

프로젝트 안에 구조화된 업무 체계가 생성됩니다.

### 3단계. 아침 업무보고

구성원은 출근 후 오늘 수행할 WBS 업무를 선택하고 계획을 등록합니다.

### 4단계. 실시간 업무 수행

상태 변경, 이슈 등록, 지원 요청, 산출물 업로드가 발생합니다.

### 5단계. 퇴근 전 업무일지

실제 수행 결과와 진척률을 기록합니다.

### 6단계. 자동 집계

프로젝트 진척도, 일정 편차, 지연 원인, 개인별 진행 상태, 팀별 업무량이 실시간 반영됩니다.

### 7단계. 평가 근거 누적

WBS, 산출물, 승인 이력, 품질, 협업 기여가 평가 근거로 자동 축적됩니다.

---

## 6-2. 왜 WBS가 중심이어야 하는가

많은 시스템은 업무보고는 있어도 프로젝트 진척도는 계산하지 못합니다. 그 이유는 보고가 **자유 텍스트**이기 때문입니다.

진비즈 ERP에서는 아래처럼 고정합니다.

> **업무보고와 업무일지는 반드시 WBS에 연결된다.**

이렇게 해야 아래가 가능합니다.

* 계획 대비 실제 진척도 계산
* 지연 원인 누적
* 직무별 업무량 비교
* 산출물 근거 축적
* 평가 데이터 자동 생성

---

# 7. 맞춤형 WBS 고도화

## 직무·직군·업무별 WBS를 다르게 설계

사용자가 지적한 대로 WBS는 전 직무 동일 양식으로 운영하면 실패합니다. 기획, 디자인, 개발, AI, 운영, 경영지원은 업무 성격이 전혀 다릅니다.

따라서 이번 최종안에서는 WBS를 아래처럼 **3층 구조**로 설계합니다.

---

## 7-1. WBS 3층 구조

### 1) 공통 코어

모든 직군이 공유하는 최소 항목

* 프로젝트
* 업무명
* 담당자
* 시작일
* 종료일
* 상태
* 우선순위
* 가중치
* 선행업무
* 승인 필요 여부
* 산출물
* 계획 진척률
* 실제 진척률

### 2) 직군 프로필

직군별로 필요한 필드 세트

### 3) 업무 스타일

같은 직군 안에서도 업무유형별로 다른 진행 방식

예를 들어:

* 기획 문서형
* 디자인 리뷰형
* 프론트 구현형
* 백엔드 API형
* AI 실험형
* 운영 반복형
* 영업 파이프라인형
* 결재 증빙형

즉, 하나의 WBS 엔진 위에 **직군 프로필 + 업무 스타일**을 얹는 구조입니다.

---

## 7-2. 직군 분류 최종안

* 경영/사업개발 직군
* 기획/PM 직군
* 디자인 직군
* 프론트엔드 직군
* 백엔드/인프라 직군
* AI/데이터 직군
* 운영/콘텐츠/CS 직군
* 재무/인사/경영지원 직군

---

## 7-3. 직군별 WBS 스타일 최종안

### 경영/사업개발 직군

기본 스타일: 파이프라인형 + 승인형

### 기획/PM 직군

기본 스타일: 문서형 + 마일스톤형

### 디자인 직군

기본 스타일: 시안-피드백-확정형

### 프론트엔드 직군

기본 스타일: 구현형 + 티켓형

### 백엔드/인프라 직군

기본 스타일: API형 + 구조형 + 안정성형

### AI/데이터 직군

기본 스타일: 실험형 + 성능형

### 운영/콘텐츠/CS 직군

기본 스타일: 반복 처리형 + SLA형

### 재무/인사/경영지원 직군

기본 스타일: 승인형 + 증빙형

---

## 7-4. 업무유형별 WBS 스타일 코드

* `PLAN_DOC`
* `PM_MILESTONE`
* `DESIGN_REVIEW`
* `FE_DEV`
* `BE_API`
* `AI_EXPERIMENT`
* `OPS_SLA`
* `SALES_PIPELINE`
* `FIN_APPROVAL`
* `HR_PROCESS`

이렇게 해야 생성 시 자동으로 필요한 필드와 화면 뷰가 달라집니다.

---

## 7-5. 맞춤형 WBS 생성 방식

### 1) 프로젝트 유형 선택

* 홈페이지 프로젝트
* ERP 프로젝트
* 플랫폼 개발 프로젝트
* 외부 협업 프로젝트
* 운영 개선 프로젝트

### 2) 참여 직군 선택

예:

* PM
* 디자인
* 프론트엔드
* 백엔드
* 운영

### 3) 템플릿 자동 생성

직군별 WBS 묶음이 자동 생성됩니다.

### 4) 업무 스타일 자동 적용

각 업무는 적절한 WBS 스타일을 가집니다.

즉, 사용자가 WBS를 맨땅에서 다 만드는 게 아니라 **프로젝트 유형 + 직군 선택만으로 70% 기본 골격이 자동 생성**되는 구조가 가장 현실적입니다.

---

## 7-6. 진척도 계산 방식도 직군별로 다르게 본다

모든 직군에 똑같은 % 계산을 적용하면 부정확해집니다.

### 공통 프로젝트 진척도

프로젝트 전체 진척도는 **WBS 가중치 × 실제 진척률**로 계산합니다.

### 직군별 보정 예시

* 기획/PM: 마일스톤 기준 비중 큼
* 디자인: 시안 확정 라운드 반영
* 프론트/백엔드: PR 머지 + QA 통과 + 배포 반영 비중
* AI: 실험 수행보다 성능 검증 완료 비중
* 운영: 처리량보다 SLA 준수율 비중
* 재무/지원: 처리량보다 정확도와 누락률 비중

즉, 같은 80%라도 의미가 다르기 때문에 **직군별 진척 판단 로직 자체가 달라야 합니다.**

# 9. 인사평가 체계

## 가장 이상적이고 공평한 방식으로의 설계

사용자가 요청한 “가장 이상적이며 공평한 인사평가 방식”은 한 문장으로 정리됩니다.

> **전 직원을 같은 잣대로 비교하지 않고, 각자의 역할에 맞는 기대치로 평가하되, 근거는 WBS·산출물·일정·품질·협업 데이터로 남기는 방식**

즉, 공정한 인사평가는 “누가 더 많이 말했나”가 아니라 “누가 맡은 역할을 어떤 난이도와 조건에서 얼마나 신뢰도 있게 수행했나”를 보는 구조여야 합니다.

백엔드 가이드도 모든 평가는 근거 데이터에 연결돼야 하고, WBS·산출물·일정·품질 기반이어야 한다고 명확히 정리합니다. 

---

## 9-1. 인사평가 기본 원칙

* 직군별 기대치가 달라야 한다
* 결과와 과정 둘 다 봐야 한다
* 보고 자체는 근거 자료이지 점수의 본체가 아니다
* 외부 변수와 난이도를 보정해야 한다
* 강제 상대평가를 최소화한다

---

## 9-2. 평가의 최종 구조

### A. 공통 평가 40

* 일정 신뢰도
* 실행 안정성
* 업무 투명성
* 조직 운영 기여

### B. 직무특화 평가 35

직군별 다르게 설계

### C. 프로젝트 기여 평가 15

* 핵심 프로젝트 기여도
* 병목 해소 기여
* 우선순위 높은 업무 처리

### D. 협업·조직 기여 10

* 협업 매너
* 타 팀 지원
* 리뷰 참여
* 지식 공유
* 개선 제안

---

## 9-3. 평가 근거 데이터

평가는 아래 데이터에서 자동 수집됩니다.

* WBS 완료 이력
* 업무보고/업무일지
* 산출물 첨부
* 승인 이력
* 지연 사유 코드
* 재작업 횟수
* QA 결과
* SLA 기록
* 프로젝트 기여도
* 피드백 반영 이력
* 회의 후속 액션 이행률

즉, 평가자는 기억에 의존하지 않고 ERP 안의 실행 데이터로 평가해야 합니다.

* 아침 업무보고와 퇴근 전 업무일지가 실무에 맞게 작동한다.
* 프로젝트 계획 대비 실제 진척도를 실시간으로 볼 수 있다.

# 25. 5단계 배포 완료 기준 최종안

## 25-1. 1단계 배포 완료 기준 — 외부 브랜드 골격과 관리자 셸 뼈대 완성

### 포함 범위

* 관리자 셸 레이아웃
* 대시보드 기본 카드
* 공통 디자인 토큰
* 서비스 허브 메뉴 골격
* 반응형 기본 셸

### 완료 기준

* 관리자에 진입하면 CMS가 아닌 ERP 톤으로 인식
* 모바일/태블릿/데스크톱에서 관리자 셸이 깨지지 않음
* 대시보드에 오늘 통제 지표가 노출
* 서비스 허브 메뉴와 홈페이지 운영 메뉴가 분리되어 보임

* 360px~1440px 이상에서 가로 스크롤 없음

# 27. 최종 성공 기준

이 ERP가 제대로 설계되었다고 볼 수 있는 기준은 아래입니다.

* 관리자 시스템이 더 이상 CMS처럼 보이지 않는다.
* 새 홈페이지/앱이 생겨도 서비스 등록만으로 관리자에 연결된다.
* 모든 업무가 프로젝트와 WBS에 연결된다.
* 직군별로 다른 WBS 스타일이 적용된다.
* 아침 업무보고와 퇴근 전 업무일지가 실무에 맞게 작동한다.
* 프로젝트 계획 대비 실제 진척도를 실시간으로 볼 수 있다.
* 지연 원인을 코드화해서 누적할 수 있다.
* 문의가 리드와 프로젝트로 이어질 수 있다.
* 인사평가가 WBS·산출물·일정·품질 기반으로 이루어진다.
* 대표와 관리자가 “누가 바쁜지”가 아니라 “어디가 막혔는지”를 볼 수 있다.
* 외부 홈페이지와 내부 ERP가 PC·모바일·태블릿에서 모두 깨지지 않는다.
* 5개 언어 콘텐츠가 발행/검수/숨김까지 일관되게 운영된다.
* 공개 도메인 정책이 `www.jinbizman.com` 기준으로 흔들리지 않는다.
